# NTI-004: Text search over the action log's intent corpus

> **Cluster:** norn-tools

## Purpose

Every action log entry records the tool_use_description — the agent's own one-line statement of what it was doing and why — alongside the tool name and a compact summary. That is the richest signal in the log and the only one you cannot filter by: ActionLogFilter matches tool, outcome, file, since, and last, but has no text match. An agent trying to answer "where did I deal with the retry backoff?" must page the whole list. The owner's steer (2026-08-08): the log is the compressed record of what was done — searching back over it, description included, is the point. This is the within-session lexical retrieval arm: no model, no index, no new storage, just a filter over text that already exists.

## Task

Add a text field to ActionLogFilter that case-insensitively matches against the entry's tool_use_description, tool name, and Level 1 summary, AND-combined with the existing fields, working identically under scope federation. Expose the tool_use_description in compact Level 1 entries so a match is explainable from the returned row. Document the field in the action_log schema; reject it with the existing typed inapplicable-filter failure on queries where it does not apply.

## Requirements

### R1: ActionLogFilter gains a text field

ActionLogFilter SHALL gain text: Option<String>. WHEN present on a list query, an entry matches IF the filter text occurs case-insensitively in the entry's tool_use_description, its tool name, or its Level 1 summary. The field SHALL combine with every other filter field by AND, matching the documented filter contract. Matching SHALL be plain substring — no tokenisation, no ranking, no threshold to invent.

**Acceptance:**
- list with filter.text returns exactly the entries whose description, tool name, or summary contains the text case-insensitively
- filter.text combines with tool/outcome/file/since/last by AND
- An empty match returns count 0 with an empty entries array, not an error

**Files:**
- modify: crates/norn/src/session/action_log_scope.rs
- modify: crates/norn/src/session/action_log.rs

### R2: Compact entries expose the tool_use_description

Level 1 compact entries SHALL include the recorded tool_use_description under a desc key, so a text match is explainable from the returned row without a follow-up detail call. WHEN the recorded description is empty, the key SHALL be present with the empty string — the record is honest about what was written, never synthesised.

**Acceptance:**
- compact_json output includes desc with the recorded tool_use_description verbatim
- Existing compact-entry tests updated for the new key
- No code path fabricates a description where none was recorded

**Files:**
- modify: crates/norn/src/session/action_log.rs

### R3: Scope federation and schema documentation

filter.text SHALL apply identically under every scope (self, children, all, specific descendant), filtering the merged labeled entries. The action_log input schema SHALL document the field on the list query. WHEN filter.text is supplied to detail, context, mutations, follow_ups, or events, the tool SHALL return the existing typed inapplicable-filter failure — never a silent no-op.

**Acceptance:**
- A federated list with filter.text returns matching entries from multiple agents, each labeled
- The schema documents text under filter with its match fields named
- detail/context/mutations/follow_ups/events with filter.text fail with the inapplicable-filter error naming the field

**Files:**
- modify: crates/norn/src/tools/action_log.rs
- modify: crates/norn/src/session/action_log_scope.rs

## Boundaries

- SHALL NOT add ranking, scoring, or fuzzy matching — substring match only; relevance ranking is the resonance design's territory, not this filter's
- SHALL NOT index or persist anything — the filter runs over in-memory entries exactly like every existing filter field
- SHALL NOT extend the events query — event payloads are an audit contract, not the intent corpus; a later brief may revisit deliberately
- SHALL NOT truncate or normalise the stored description — match against it verbatim
