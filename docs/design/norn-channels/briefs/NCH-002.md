# NCH-002: Preserve tool selection policy through live MCP replacement

> **Cluster:** norn-channels
> **Checklist:**

## Purpose

Preserve the operator tool policy at the live source-publication boundary described by norn-channels/design.json architecture and NCH-001 R4a/R4b planning. This is the narrow policy prerequisite identified in /private/tmp/nwp-03-proof/runtime-plan.json, grounding entry tool/generation.rs. C4/S4 coverage is intentionally shared with NCH-001: this brief owns only tool selection, not channel delivery.

## Task

Implement one immutable original exact-name selection policy for registry and live generations. Retain separate selected-server visibility so a refresh can admit a newly discovered tool that satisfies the original operator policy. Parent owns all Cargo and venue verification; no local compilation, commit or landing.

## Requirements

### R1: Retained allow/deny predicates and independent server views

WHEN a registry becomes an immutable generation, the generation SHALL retain the actual original allow-list and deny-list, including names not yet discovered and the distinction between no allow-list and an empty allow-list. WHEN dynamic tools are replaced or removed, the successor SHALL enforce that retained policy before constructing executable, provider, prompt, discovery and scheduling surfaces. Explicit deny SHALL win. Initial MCP server selection SHALL remain a view over permitted tools, not overwrite the original policy with a snapshot of present names. Selected-server replacement candidates SHALL determine membership in that server view. Child generation views SHALL retain the original policy and intersect explicit child name restrictions without treating the parent server view as authority over independently selected servers. Duplicate dynamic and stable-name collision checks SHALL remain active before policy filtering. An excluded tool SHALL fail dispatch with ToolNotFound and absent effect lookup SHALL stay Unknown.

**Acceptance:**
- A registry allowing future names and denying one allowed name produces a replacement that admits the future permitted tool and refuses denied and unlisted tools; none of the refused tools appear in definitions, prompt, dynamic prompt or ordinary tool catalog entries.
- No allow-list admits newly discovered names; an explicit empty allow-list admits none. Matching remains exact, with no prefix or wildcard expansion.
- Removing then replacing tools preserves the original predicates. A registry edit after snapshot does not mutate an existing generation policy.
- A child view enforces original allow/deny policy and any child name restriction through later replacement, while a different explicitly selected MCP server remains selectable when policy permits.
- The actual McpRuntimeCandidateBuilder selected-server path admits a newly discovered permitted tool despite a narrowed startup registry; deny-list and allow-list constraints survive that same candidate path.
- Denied or unlisted dynamic tools cannot execute, return ToolNotFound, and have Unknown scheduling effects. Candidate duplicates and stable-name collisions remain explicit errors.
- No source in the NCH-001 delivery wall changes, except the separately coordinated one-line mcp_runtime.rs call from set_available to set_visibility. No local Cargo or commit runs.
