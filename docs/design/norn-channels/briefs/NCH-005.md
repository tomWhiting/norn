## Purpose

Bind explicitly opted-in channel sources to the actual registered Norn root and publish their first runtime through the existing serialized MCP actor.

## Task

## Requirements

### R4b: Root-before-MCP startup and explicit initial activation

WHEN explicit channel settings accompany a new root, assembly SHALL resolve the registered root identity before installing the session inbox. The existing serialized MCP control actor SHALL explicitly initialize its first candidate, publish matching tools/runtime, then activate staged channel ingress. Unchanged configuration reload SHALL retain its existing semantics. No parallel runtime, fabricated UUID, implicit policy or implicit capacity is introduced.

**Acceptance:**
- A configured channel startup installs one inbox only after resolving the authoritative registered root UUID, and fails without retained MCP configuration or with a preconnected runtime.
- Explicit positive budgets, source names, policy and overflow survive assembly without defaults or fabricated recipient identity.
- Channel-enabled candidate connections install their source listener before transport spawn; ordinary servers use the existing connect path.
- The initial control command builds and publishes a candidate even when configuration has not changed; later successful initializations are idempotent.
- Channel ingress activates after tool generation and runtime publication; removed/replaced sources are retired, reused clients remain live.
- Failed connection or generation publication is explicit and cannot silently claim initialized success; retries do not mint a parallel runtime.
- Candidate16 model-selection changes in builder/build.rs are preserved. Tests cover actual root identity, invalid startup, and explicit initialization versus unchanged reload.
- A real Rust stdio fixture emits before initialization completes; a built registered Agent explicitly initializes its existing MCP actor, sees matching reply tools, and persists the initial source-attributed message into its first provider request.
- Only the explicitly channel-bound root controller manages channel activation and retirement; a child inheriting MCP tools does not acquire authority over the root inbox lifecycle.
- Approval and revocation preserve durable approval rollback when tool generation publication fails; after successful generation publication they publish the matching runtime and execute the same owner-scoped channel activation or retirement as startup.
- All removed or replaced sources are retired before candidate activation; every transition is attempted and all failures are reported without abandoning later revocations.
- Post-publication channel errors identify the committed revision and cannot roll back persisted configuration or trigger refresh fallback from the previous runtime.
- Deterministic retired reused-source regressions cover revoked-source admission fencing, durable approval, session and persisted configuration, matching runtime/tool revision, and a subsequent source activation despite earlier failures.
